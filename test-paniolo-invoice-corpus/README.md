# Public invoice test corpus

168 unchanged invoice files from three public repositories, retrieved on 2026-10-30:
UBL Invoice, UBL CreditNote, CII, and hybrid Factur-X/ZUGFeRD PDFs. The corpus supplements
invoices generated by unit tests with third-party business cases, published negative
examples, and legacy compatibility cases.

**Results: 149 files pass the selected validation profile; 19 are rejected.
Paniolo currently cannot read 57 valid files into its invoice model.**
A passing corpus test confirms the documented baseline, including these known limitations.
It does not establish full format conformance for Paniolo.

## Running the tests

From the repository root, using Java 21 and Maven:

```sh
mvn -Pinvoice-corpus -pl test-paniolo-invoice-corpus -am test
```

To run only the 169 corpus checks (168 invoices and one manifest check):

```sh
mvn -Pinvoice-corpus -pl test-paniolo-invoice-corpus -am test \
  -Dtest=PublicInvoiceCorpusTest -Dsurefire.failIfNoSpecifiedTests=false
```

With a populated Maven cache, add `-o` to run offline. The tests themselves do not
download invoices. The first build requires network access for Maven dependencies and
the existing rules bundle module. The profile is opt-in; this module is neither
installed nor published.

Each run writes `results.tsv` and per-invoice XML validation reports under
`target/corpus-report/`, including rule identifiers, severity, validation stage, and
location. `*.automatic.xml` also records the result of `Paniolo.validate(bytes)`.

## What is checked?

- SHA-256 hashes of the original files and complete, unique manifest coverage.
- KoSIT and Mustang files: automatic validation through the Paniolo facade.
- Connecting Europe files: an explicit EN 16931 profile using Paniolo's `InvoiceValidator`,
  plus a separate check of the automatic facade. For these general EN/Peppol examples,
  the facade frequently selects the stricter XRechnung profile.
- Validity against fixed expectations. Rejected files must produce selected, reviewed
  error identifiers. An arbitrary exception does not count as successful rejection.
- Valid files: reading through `Paniolo.read(bytes, ReadMode.LENIENT)`.
  Known read failures are compared by exact exception type and message. Fixing a limitation
  therefore initially fails the test and requires a deliberate expectation update.

`LENIENT` does not guarantee full conversion support. Successful reads are not checked
for field-level model fidelity or lossless round trips. Additional amount recalculation
(`calculationCheck`) is disabled.

For PDFs, the container and embedded XML are checked; **PDF/A conformance is not checked**
(`PDFA-NOT-CHECKED`), because `paniolo-pdfa` is not on the corpus classpath. A PDF passing
these tests is therefore not proof of full PDF/A conformance.

The original files are retained under `src/test/resources/corpus/`, preserving their
upstream subdirectories. The selection includes all 86 KoSIT XML files from `src/test`,
all 63 XML files (including `.XML`) from the EU directories `ubl/examples`, `cii/examples`,
and `test/testfiles`, and 9 XML files plus 10 PDFs selected from Mustang's validator test
resources. The EU rule test fragments under `test/Invoice-unit-UBL` and similar directories
are not complete invoices and were not included as invoice files. No errors were
introduced into the retained files.

[manifest.tsv](src/test/resources/corpus/manifest.tsv) records each invoice's commit-pinned
download URL, SHA-256 hash, expected validity, required error identifiers, read result,
known exception, automatic validity, and finding notes. `valid` means the expected
**current Paniolo result under the selected profile**, rather than a general upstream
claim about the file. In particular, the two CVD references and some historical Mustang
positive examples are documented as compatibility findings in the `note` column.

License texts and the Mustang NOTICE are retained under `corpus/licenses/`. The EUPL
continues to apply to the retained EU files; they are not relicensed under the project
license. Corpus metadata and test expectations were added here; the invoice bytes are unchanged.

## Verifying and restoring fixtures

```sh
python3 test-paniolo-invoice-corpus/scripts/fixtures.py
python3 test-paniolo-invoice-corpus/scripts/fixtures.py --restore
```

Without options, the script verifies invoice and license file hashes locally. `--restore`
downloads only missing or changed originals from the pinned GitHub URLs, verifies the
bytes before writing them, and leaves expectations unchanged. Updating upstream versions
requires deliberate changes to files, sources, hashes, and reviewed expectations;
test runs never generate new expected values.
